# 배포 — 제출물을 어떤 형태로 내보내는가

이 프로젝트는 웹 서비스가 아니라 **논문과 재현 패키지**다. 그래서 "배포"는 *"채점자가 아무것도 설치하지 않고 결과를 확인할 수 있게 만드는 일"*을 뜻한다.

---

## 1. 배포 형태 비교

| 후보 | 장점 | 단점 | 채택 |
|---|---|---|---|
| **단일 ZIP 파일** | 로그인·계정·인터넷이 필요 없다. 과제 요구(C48)가 ZIP 한 개다. 원자료를 그대로 넣어도 라이선스 문제가 없다 | 파일이 크면 열기 번거롭다 | **채택** |
| GitHub 저장소 | 링크 하나로 공유. 이력이 남는다 | 공개로 전환하면 C51(로그인 없이 열림) 충족. 줄바꿈 변환을 반드시 차단해야 한다(`.gitattributes`) | **병행** — private로 올림 (2026-09-11) |
| 웹 대시보드 배포 | 결과를 눈으로 바로 봄 | 서버 비용·계정이 생기고, 검증할 것이 늘어난다. 논문 과제에 불필요 | 기각 |
| 노트북(.ipynb) | 실행과 설명이 한 파일 | Jupyter 설치가 필요하다. "설치할 패키지 없음"이라는 장점을 잃는다 | 기각 |

**결론: ZIP 한 개.** URL 형태의 제출물을 만들지 않는다(C51은 자동 충족).

---

## 2. 왜 "설치할 패키지 없음"을 고집했나

재현 패키지의 가치는 **채점자가 실제로 돌려 보는지**에 달렸다. `pip install` 단계가 하나만 있어도 대부분 거기서 멈춘다.

그래서:

- 통계를 scipy 대신 직접 구현했다 (`src/stats.py`, 자체 검증 내장)
- 그림을 matplotlib 대신 SVG 문자열로 직접 만들었다 (`src/analyze.py`)
- 데이터 형식을 JSONL / JSON / CSV로 두었다 (표준 라이브러리로 읽힌다)

대가: 통계 구현이 맞는지 스스로 증명해야 한다. `python src/stats.py`의 자체 검증이 그 역할을 한다.

## 3. 제출 절차

```bash
python src/score.py --all        # 원자료 채점
python src/analyze.py            # 표·그림 생성
python src/check_submission.py   # 기계 점검 (전부 통과해야 한다)
python src/package.py            # ZIP 생성 + 매니페스트 기록
```

`package.py`는 ZIP을 만든 뒤 **다시 열어 필수 파일이 전부 들어갔는지 확인**하고, 본 실행 원자료가 720개인지 세어 본다. 하나라도 어긋나면 종료 코드 1로 실패한다.

### 마지막 확인 (반드시 한다)

ZIP을 **다른 폴더에 풀고** 거기서 돌려 본다.

```bash
cd <다른 폴더>
python src/verify_prereg.py
python src/score.py --all
python src/analyze.py
```

표와 그림이 원본과 같게 나와야 한다.

## 4. ZIP에 넣는 것과 빼는 것

**넣는 것**

| 대상 | 이유 |
|---|---|
| `data/raw/trials/*.json` (720개) | 원자료. 프롬프트 전문과 원출력 전문이 들어 있다 |
| `data/pilot_v1/`, `data/pilot/` | 예비 실행 원자료. **설계를 왜 바꿨는지에 대한 증거**라 뺄 수 없다 |
| `data/raw/scenarios.jsonl`, `prompts.jsonl` | 입력 자료 |
| `data/raw/reference_check_arxiv.json` | 참고문헌 조회 응답 원본 |
| `data/raw/timestamps_manifest.json` | 사전등록 선후 증거 (아래 5절) |
| `src/` 전체, `docs/` 전체, `results/`, `논문/`, `README.md`, `run_all.sh` | 재현과 설명에 필요 |

**빼는 것**: `__pycache__`, `.pyc`, 실행 로그(`*.log`), 자기 자신인 ZIP, OS가 만든 잡파일.

## 5. ZIP이 지워 버리는 증거를 지키는 법

이 연구의 증거력은 **"사전등록이 원자료보다 먼저 만들어졌다"**에 달려 있다. 그런데 **ZIP을 압축 해제하면 모든 파일의 수정 시각이 해제 시각으로 덮인다.** 패키지 안에서는 선후 관계가 사라진다.

그래서 `package.py`가 ZIP을 만들기 직전에, **원본 파일시스템에서 읽은 시각과 SHA256**을 `data/raw/timestamps_manifest.json`에 굳혀서 함께 넣는다. `verify_prereg.py`는

1. 파일 시각이 쓸 만하면 파일 시각으로 확인하고,
2. 시각이 뭉개져 있으면(= ZIP 사본이면) 매니페스트로 확인하되,
3. 어느 쪽이든 **현재 파일의 SHA256이 매니페스트 기록과 같은지**를 함께 검사한다.

즉 패키징 이후 사전등록이나 원자료를 한 글자라도 고치면 검사가 실패한다.

> **한계를 분명히 해 둔다.** 이 매니페스트도 결국 연구자 본인이 만든 파일이다. 외부 기관(OSF 등)에 등록한 것만큼의 증거력은 없다. 논문에도 같은 내용을 적었다.
